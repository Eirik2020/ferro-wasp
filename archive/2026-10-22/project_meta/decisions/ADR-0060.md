# ADR-0060: Crates Follow The Safety-Critical Split And Own Their Tasks

Status: accepted, not yet implemented; crate map amended by ADR-0061, task placement by ADR-0065

Decided by the user on 2026-10-17. Names are working names until each crate is
created.

Task definitions live in their subsystem's crate behind a `tasks` cargo
feature. Task code is target-only (`rtic` with the thumbv7 backend,
`cortex-m`, `defmt`), and the logic stays host-tested without the feature.
`ferrowasp-stm32-tasks` and its shared prelude dissolve; each task imports only
what its own crate depends on.

The safety-critical core splits along bench-evidence lines, so a filter change
leaves the arming evidence standing:

| Crate | Holds |
|---|---|
| `ferrowasp-safety` | safety master, coordinator, arming, actuator authority |
| `ferrowasp-control` | general control: PID, filters, notch-bank maths, estimator algorithm, bias and level calibration maths, frame rotation |
| `ferrowasp-flight-control` | flight-controller-specific: control loop, rates, tuning profile, mixer, dynamic idle, RPM filter wiring |
| `ferrowasp-input` | Command Input, RC protocol trait, RC group |
| `ferrowasp-feedback` | actuator feedback core, ESC-telemetry trait and group |
| `ferrowasp-imu` | IMU trait and group, plus one driver crate per sensor |
| `ferrowasp-output` | DShot and PWM output groups, waveform encoding, bidirectional decode |
| `ferrowasp-serial` | UART transport group, RX reader, TX writer |
| `ferrowasp-config` | ADR-0059 |

There are three contract crates:
- `ferrowasp-io-contracts` (safety-critical, ADR-0057);
- `ferrowasp-boundary-contracts` (safety-critical: `Request`, results, and the
  messages to the observer);
- `ferrowasp-protocol` (non-critical but W6: the wire protocol and blackbox
  format). FerroConfigurator depends on it instead of the core.

Ledger topics live in the observer crate. Messages between safety-critical
tasks live in their core crates. CRSF, SBUS, and BLHeli telemetry are
standalone protocol crates (ADR-0057).

Each chip backend splits into `ferrowasp-stm32-critical`,
`ferrowasp-stm32f4-critical`, and `ferrowasp-stm32h7-critical`:
- the critical crates take DShot and timer DMA, SPI, EXTI, UART, clocks,
  timebase, watchdog, board routes and manifest, DMA memory, and
  `system_reset` and `system_bootloader`;
- the non-critical `ferrowasp-stm32`, `-stm32f4`, and `-stm32h7` keep USB, the
  status LED, the ADC, and storage.

The non-critical crates are `ferrowasp-observer`, `ferrowasp-blackbox`,
`ferrowasp-storage` (flash manager, config save, NOR storage), `ferrowasp-cli`,
`ferrowasp-osd`, `ferrowasp-mspv1`, `ferrowasp-mspv2`, and `rc-pwm`.

`ferrowasp-core`, `ferrowasp-io-core`, `ferrowasp-flight`, `ferrowasp-drivers`,
`ferrowasp-pid`, `ferrowasp-waveform`, and `ferrowasp-stm32-tasks` dissolve
into the crates above.

The redesign lands as its own stack of changes on `main`, apart from the
requirements tooling. It changes the flight image, so it re-gates the Foxeer.
