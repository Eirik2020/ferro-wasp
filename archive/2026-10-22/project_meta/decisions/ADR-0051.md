# ADR-0051: Verification Levels Are One Enum And Only Gates Block

Status: accepted; implemented in tools/reqtool except the analysis-level checks

Decided by the user on 2026-10-17. One list of levels replaces both the old
validation tiers and the levels proposed in the requirements plan, ordered by
cost and risk:

| Level | Meaning | Replaces |
|---|---|---|
| `analysis` | tool checks on source and images: dependency direction, the priority rule, stack, RAM and flash, the image building for its board and features | `embedded-build`, part of `software` |
| `unit` | host tests, including conformance suites against mocks and golden fixtures | `software` |
| `sitl` | software-in-the-loop on the host, once a harness exists | none |
| `mcu` | on the flight controller, nothing actuating | `bench-unpowered` |
| `bench` | the full drone, ESCs powered, propellers removed | `bench-powered-props-off` |
| `flight` | in flight | `flight` |

Each verification entry also names a `target` (`host`, `fcu`, later `devboard`)
and a `setup` (`none`, `sim`, `props-off`, later rigs). A devboard or
peripheral-simulator stage is then a new value, not a new level or a migration.

`preflight` is no longer a level. A level says how a requirement was verified;
preflight says whether this exact image and configuration may fly now. It
becomes a gate.

Gates are named checkpoints, such as merge, bench session, preflight and
flight. Each declares which requirements, at which levels and for which
variants, must be `verified` before it opens. Only gates block. Missing
evidence never blocks development, so evidence needing equipment that does not
exist yet (such as a timing devboard) holds nothing back until a gate asks for
it.

W7 still applies at every level: a compile does not establish target
behaviour, a target boot does not establish actuator behaviour, and props-off
operation does not establish flight readiness.
