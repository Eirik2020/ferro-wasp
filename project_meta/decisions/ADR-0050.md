# ADR-0050: Requirement Status Is Computed From Evidence, Never Recorded

Status: accepted; implemented in tools/reqtool

Decided by the user on 2026-10-16/17, as a clean-sheet design rather than an
extension of the component registry.

FerroWasp tracks requirements, the items they are allocated to, the methods
that verify them, and the evidence those methods produce. People and agents
write requirements. Only `reqtool record` writes evidence. Nobody writes
status: `reqtool` computes it for each requirement, verification entry, and
variant from the links, the evidence records, and the current fingerprints
(ADR-0052). Gates read the computed status (ADR-0051).

| Status | Meaning |
|---|---|
| `verified` | a pass exists whose fingerprint matches the current code |
| `stale` | a pass exists, but its fingerprint no longer matches |
| `unverified` | no evidence exists |
| `failed` | the newest evidence at the current fingerprint is a fail |

`stale` and `unverified` stay distinct: re-running a test that passed before is
different work from testing something never tested.

A fail at the current fingerprint is cleared only by a pass at a new
fingerprint, or by a superseding record on the user's explicit ruling that
cites the fail. A pass after a fail with nothing changed does not clear it; a
flaky result counts as failed. Never change a result to make a gate appear
complete.

Evidence does not expire with age. A pass stands while its fingerprint matches.

Missing evidence is `unverified`, never N/A. It never blocks development; only
a gate that requires it blocks.

Reasons:

- stored status drifts silently from the code; computed status cannot;
- a hand-maintained component registry lets a record forget a dependency, so
  a pass can survive a change it should not (ADR-0038's weakness);
- with status computed, no `invalidate` step exists to be forgotten.

ADR-0038's goal stands: evidence for unchanged code is never re-owed, on any
board. Only its mechanism, the hand-listed `COMPONENTS.json`, is replaced.
