# ADR-0054: Safety-Critical Code Is Separated By Crate And Never Depends On Non-Critical Code

Status: accepted, not yet implemented; priority rule amended by ADR-0061

Decided by the user on 2026-10-16/17.

Code is classified on two axes: safety-critical or non-critical, and HAL-free
core or hardware. For the path UART → Command Input → control loop → actuator
authority → DShot, the UART and DShot DMA code are hardware and the rest is
core. A hardware change must not re-certify the core, while the whole path is
still certified by path evidence (ADR-0052).

The direction rule: a safety-critical crate never depends on a non-critical
crate. A non-critical crate may depend on a safety-critical one. Cargo enforces
it, and `reqtool` checks it from `cargo metadata`. Crates, not modules, carry
the boundary: within one crate nothing stops a module naming another, and
`pub(crate)` cannot express the rule.

Naming: the class is `critical`, written "safety-critical" in prose. No new
code uses bare "critical" for anything else. `safe` (Rust's unsafe), `safety`
(a crate name), `flight` (a crate and a level), `certified` (a status) and
`trusted` (external code) were rejected. `[package.metadata.ferrowasp]
critical = true` in each crate's `Cargo.toml` is the source of truth. The
`-critical` suffix appears only on split pairs, such as
`ferrowasp-stm32f4-critical` beside the non-critical `ferrowasp-stm32f4`, and
`reqtool` checks that names and metadata agree.

Every item in a safety-critical crate must trace to a requirement; `reqtool`
fails otherwise. Reclassification is deliberate: when safety-critical code needs
something non-critical, the direction check fails until that code is moved and
gets its requirements.

The priority rule: the observer and every non-critical task run below the
lowest safety-critical task, and the `app!` parser checks it. Moving
`esc_manager_task` above `usb_fs` is a priority change that needs a timing
rationale and revalidation.

The bus rule: a bus carrying a safety-critical device carries no non-critical
device. The board data tests enforce it; an exception needs the user's
approval. The Foxeer (IMU on SPI1, flash on SPI2) and the Lucid (IMU on SPI1,
SD on SDMMC) comply.

Classified safety-critical: actuator feedback (eRPM qualifies arming); the
attitude estimator and accelerometer level, since stabilized mode is next;
`system_reset` and `system_bootloader`. In rate mode an estimator fault must
not affect motor output; angle-mode fault handling is decided with angle mode.
Non-critical for now: `adc` (battery voltage and current, display only) and
`pwm_config` (servo PWM).
