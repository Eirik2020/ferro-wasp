# ADR-0055: Tasks Communicate Over Declared SPSC Links And Single-Writer Flags

Status: accepted, not yet implemented; generalizes ADR-0015, amends ADR-0010

Decided by the user on 2026-10-16/17.

Every link between safety-critical tasks, and from a safety-critical task to
the observer (ADR-0056), is a single-producer, single-consumer queue. Its
producer handle and its consumer handle are each an RTIC local resource of
exactly one task and cannot be cloned, so the compiler enforces SPSC.
ADR-0010's critical-section mailbox becomes SPSC request and response queues.

- Every message carries a timestamp and a sequence number.
- Each link declares its kind:
  - `state`: the consumer drains the queue, keeps the newest message, and
    checks its age against the link's limit. An empty queue means nothing new,
    not an error; too old is stale, and stale fails closed;
  - `event`: every message is processed in order. A full queue is a counted
    fault.
- On a full queue the producer drops the new message, counts it, and never
  blocks (W2).
- Kind, depth, and age limit are requirements for each link, with depth
  derived from the producer and consumer rates.

Atomic flags remain for one-writer, many-reader, single-word state such as
"armed". The writer handle is a local resource of one task, and each reader
handle is a local resource of its task, so the parser sees every flag. A flag
never carries multi-field data; separate atomics can tear, as roll, pitch and
yaw can in `snapshots.rs` today. A flag has no timestamp, so a safety-critical
task reads one only when the writer's liveness is covered elsewhere, by the
watchdog or a heartbeat link; otherwise the value travels over a `state` queue.
Non-critical code never writes a flag that safety-critical code reads.

Global `static` atomics that any task can touch, and RTIC shared resources
locked by both safety-critical and non-critical tasks, are retired. Today
`tuning_profile` is locked by `control_loop` (14), `rc_input` (10),
`osd_refresh` (3), and `flash_manager_task` (1), so a non-critical task can
hold a lock the control loop needs.

Reasons:

- the parser reads the whole communication graph from `app!`, which path
  fingerprints and the direction checks need;
- a non-critical task that shares no resource with a safety-critical one
  cannot block it through a priority ceiling.
