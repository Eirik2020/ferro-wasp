# ADR-0043: The Command Line Reboots Into The STM32 ROM Bootloader

Status: accepted

Amends ADR-0022: holding BOOT is no longer the only way into ROM DFU; it stays
the recovery path. Extends ADR-0042's command line with `reboot` and
`reboot dfu`.

The goal (user, 2026-10-15) is Betaflight Configurator's experience: plug in a
computer, then flash or reboot the board from the configurator. FerroWasp gets
it the way Betaflight does on F4 and H7 targets: on command, the firmware
restarts into the chip's ROM bootloader, which enumerates as a USB DFU device,
and the configurator flashes through it. There is no FerroWasp bootloader;
every image still links at the start of internal flash. A custom bootloader
was rejected: it moves every flight image's link address and adds its own USB
stack and update failure modes for nothing ROM DFU lacks.

The user chose the text command line over the MSPv2 `Reboot` request
(2026-10-15), and a configurator that flashes its bundled image or a file the
user picks, not downloaded releases.

`reboot` and `reboot dfu` are USB-only. The flash manager accepts one only
while disarmed, with no flash maintenance or flight log open; it writes out the
store's write-back buffer, waits at most 500 ms for the last program, answers,
and resets. A request word in RAM that startup does not initialize survives
the software reset. The first thing `init` does is check it: only after a
software reset and only for the exact word does it stop SysTick and every
interrupt and jump to system memory, before clocks or any peripheral is set up,
so the motor pins are in their reset state as at power-on. After any other
reset the word is cleared unread. The jump and the word are each chip
backend's unsafe code: `system_bootloader` in `ferrowasp-stm32f4` (system
memory at `0x1FFF0000`, remapped to address 0) and in `ferrowasp-stm32h7`
(`0x1FF09800`).
