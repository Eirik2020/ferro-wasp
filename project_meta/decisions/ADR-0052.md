# ADR-0052: Fingerprints Are Derived, And Parents And Children Verify Each Other

Status: accepted, not yet implemented

Decided by the user on 2026-10-16/17.

A fingerprint is the identity of what a piece of evidence covered. `reqtool`
derives it; nobody lists it. Its scope depends on the verification entry:

- **unit or core:** the allocated item's crate and its dependency closure, the
  toolchain, and the locked external versions. This is sound because a
  safety-critical crate depends only on safety-critical crates and pinned
  externals (ADR-0054).
- **hardware conformance**, per MCU family: the `-critical` backend crate,
  `ferrowasp-io-contracts`, and the chip.
- **path:** every segment crate on the path, the board data crate, the
  safety-critical part of the RTIC scheduling table (priorities, bindings and
  link graph, read from `app!`), and the variant values.

A requirement's own text is part of the fingerprint: changing its statement or
its verification entry makes its evidence `stale`.

Image-level properties come from linking everything together, so no crate
fingerprint covers them. Stack, RAM and flash usage are checked for each board
image in CI at the `analysis` level.

Variants are runtime-selected options that change which code runs, such as the
RC protocol, the actuator-feedback source, serial bindings and the loop rate.
They are declared once. A verification entry lists the variants it covers;
omitted means variant-independent. Coverage is reported for each variant a
board can run.

Verification modes:

| Mode | Direction | Requires |
|---|---|---|
| `direct` | the requirement's own evidence | none |
| `via_children` | up: children jointly sufficient | a stated reason |
| `covered_by_parent` | down: the parent's run covers the child | a named observable and a reason |
| `either` | either of the above | none |

`covered_by_parent` covers only what the parent's run actually exercised and
observed. A fault path, such as rejecting stale RC, always needs its own
evidence. The tool cannot judge sufficiency or observation; the stated reason
records that judgement.

Timing: either prove that the parent path runs as expected, or prove that each
child task's execution budget is within tolerance. Budgets need a dedicated
devboard. Until one exists, timing is covered from the parent, by counters
every bench and flight run records: queue drops, stale samples and loop
overruns. A non-zero count on a safety-critical link fails the run. While
timing is covered from the parent it is not compositional: a change to any
safety-critical task on or above a path re-owes that path's timing evidence.
