# ADR-0058: The Control Loop Is Gyro-Synced

Status: accepted, not yet implemented; supersedes ADR-0008's control scheduler, its TIM2 I/O timebase stands

Decided by the user on 2026-10-17, following Betaflight, whose scheduler locks
to the gyro's data-ready interrupt. That is to be confirmed in Betaflight's
source at implementation.

The control loop runs when a new `ImuSample` arrives over its link, not on a
TIM4 tick. This removes the free-running timer, the `TimerTick`
acknowledgement trait in the core, and the stale ticks that came from the
ICM-42688-P running about 1% fast against the 2 kHz timer (the 2026-10-09
bench, which beat every ~89 samples).

Fail-closed by construction: if the IMU stops, no samples arrive, the control
loop sends no `MotorCommand`, and the output group's freshness check stops the
motors (ADR-0057). A control-loop heartbeat over a `state` link lets the safety
master disarm and report why.

The loop rate is the sensor's output rate divided by an integer N:
- it may not exceed the board's highest timing-tested rate. Execution time
  does not depend on the rate, so every lower rate inherits that timing
  evidence;
- it may not fall below a minimum the core declares for its filters and
  control.

`validate()` checks the configured rate at boot (ADR-0059). Filters, the RPM
filter and the PID use measured sample intervals, not the nominal rate.
Rate-dependent logic is unit-tested at every rate the sensor offers. At low
rates this includes the RPM filter's Nyquist limit, so filtering happens at the
sensor rate before the samples are thinned out.

Per the datasheets as recalled, not yet checked: 500 Hz, 1, 2, 4 and 8 kHz
are possible on the MPU-6000 and ICM-42688-P, and 3 kHz is not.

This changes loop scheduling and loop rate (W6). It needs the props-off checks
and a flight re-gate.
