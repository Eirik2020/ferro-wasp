# ADR-0035: Board Support Lives With Each Isolated App

Status: accepted

The standalone `ferrowasp-bsp` crate is removed. The term BSP was overloaded,
and a cross-board crate added an ownership layer without providing a useful
dependency boundary. Each isolated firmware package now owns its immutable
board facts under `apps/<app>/src/board/` and exposes its support surface from
`src/lib.rs`.

The dependency direction for STM32F4 firmware is:

```text
stm32f4xx-hal -> ferrowasp-stm32f4 -> app support -> RTIC app shell
                         ^                 ^
                         |                 |
              reusable common crates   board facts
```

`ferrowasp-stm32f4` owns reusable STM32F4 mechanisms and configuration types.
The app support library selects the chip feature and supplies board pins,
peripherals, DMA streams, timer channels, electrical policy, orientation, and
validated board profiles. A generic `ferrowasp-stm32` wrapper is not introduced
without a concrete cross-family mechanism that needs it; `ferrowasp-mcu`
remains the existing family-neutral MCU contract layer.

Each `src/main.rs` is an RTIC shell. It may declare RTIC shared/local resources,
`#[init]`, `#[task]`, the monotonic selected by RTIC, and scheduling/locking
wiring. It imports one internal support facade. Board types, helper functions,
macros, constants, reusable algorithms, and peripheral-construction mechanics
do not belong in the shell. Initialization names the concrete pins, DMA,
peripherals, and configuration while normal support functions perform the
construction. Custom macros are not used to hide runtime behavior.

Reusable behavior must move to its narrowest shared owner: safety and domain
state to `ferrowasp-core`, protocol/device behavior to `ferrowasp-drivers`,
portable I/O contracts to `ferrowasp-io-core`, reusable task services to
`ferrowasp-tasks`, and STM32F4 mechanics to `ferrowasp-stm32f4`. Board-local
support must not become a second copy of behavior another board can use.

Foxeer F405 V2 is the golden flight app. Secondary flight apps preserve its
safety and runtime invariants unless a documented board fact requires a
difference. This ownership move does not change motor authority: only the
safety-owned actuator task and actuator hardware adapter may command motor
peripherals.

This decision supersedes ADR-0007 and the standalone-BSP ownership and location
clauses in ADR-0016. Historical BSP decisions remain as provenance for the
physical facts they recorded.
